# F17 media corpora — what they measure, and what they do not

Three corpora extend the eval suite from text-only to the modalities Feature 17
shipped: `vision-product`, `voice-support`, `media-unreadable`. They exist
because F17 shipped **unbenchmarked** (former feature plan, 2026-09-06) and
Features 19/20 (docs/GULF_PARITY_PLAN.md Phases 6-7, via the Phase 5 eval) are gated on a regression signal that covers it — F19 broadcasts
against segments built partly from vision-derived labels, and a broadcast
mistake reaches many customers at once.

## How a media case runs

A case names its attachments in `cases.json`; the runner reads the bytes from
the corpus's `media/` directory and hands them to `AgentTurnInput.media`,
exactly as `RespondPathProcessor` hands over bytes it fetched from tenant
storage. Nothing about the pipeline is special-cased for the eval: the same
whitelist, signature check, vision pre-pass, ASR step, retrieval, guardrails,
citation verification and D10 confidence run.

Two harness-side differences, both deliberate:

- **`messageText`.** A voice note carries no text, so the respond path builds
  `currentMessage` as `""`. Voice cases set `messageText: ""` and keep
  `question` as a scorecard label.
- **No standalone retrieval probe.** For a media case the query retrieval
  actually receives is the text the modality pre-pass derived, which does not
  exist until the turn runs. Probing on the caption instead would report a
  recall number for a query the product never issues, so `recallHit` stays
  `null` for these cases rather than being guessed.

## Fixture provenance

All binaries are generated by `eval/scripts/generate-media-fixtures.py` and
committed. Re-run it to re-derive or extend them.

| Fixture | How it was made | What it probes |
|---|---|---|
| `vision-product/media/x200-box.png` | Pillow-rendered product-box label | product identity → catalogue price/stock |
| `vision-product/media/s9-kettle.png` | Pillow-rendered product-box label | near-duplicate warranty clause across two products |
| `vision-product/media/injection-note.png` | Pillow-rendered note | A10's injection bar carried by an image instead of text |
| `voice-support/media/*.wav` | macOS `say` → ffmpeg 16kHz mono PCM | ASR transcript accuracy through to a cited answer |
| `media-unreadable/media/not-really-a-photo.jpg` | zip header, declared `image/jpeg` | declared-vs-signature mismatch → `media_unreadable` |
| `media-unreadable/media/truncated.png` | PNG signature and nothing else | truncated download → `media_unreadable` |
| `media-unreadable/media/silence.wav` | ffmpeg `anullsrc` | readable bytes, nothing to hear → `transcription_failed` |

## The limitation, stated plainly

The image fixtures are **rendered labels, not photographs**. They exercise the
whole path end to end with a deterministic, reviewable input, and they are
enough to catch a regression — a broken vision binding, a dropped attachment, a
guardrail that stops applying to image-derived text. They are **not** a
measurement of photographic recognition of a physical product in a customer's
hand, under real lighting, at an angle, partly occluded. That measurement needs
real customer photos, which needs real tenant traffic — the same precondition
TODOS.md gives for the suite as a whole.

Read the vision numbers as "the pipeline works and has not regressed", never as
"vision accuracy is X%".
